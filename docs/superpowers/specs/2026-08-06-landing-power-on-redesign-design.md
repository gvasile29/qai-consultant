# Landing page redesign — "Power-On Sequence" (Phase 1 of 3)

**Date:** 2026-08-06
**Status:** Approved

## Problem

The app's landing/intro screen (`app.py:render_intro()`) is the most-visible screen in the product and the only one still rendered with zero custom styling — plain `st.info()`/`st.success()`/`st.columns()` blocks on a white background. The v3.4 "Calibration Bench" redesign explicitly scoped this screen out ("the pre-existing intro/landing screen was out of scope and still renders with native Streamlit styling" — see `CLAUDE.md`'s v3.4 changelog entry). The user wants a full app redesign, decomposed into three phases (see "Scope" below); this spec covers Phase 1 only.

## Direction selection

Three independent visual directions were generated by parallel agents (via a Workflow judge-panel — see `feedback_ai_council.md`) and reviewed by the user through the brainstorming visual companion, with live CSS-animated mockups:

1. **Signal Grid** — replace the whole design system with a dark-canvas, single-saturated-accent SaaS look (Linear/Vercel register). Rejected: would discard the v3.4 token/font investment and re-litigate every already-styled screen.
2. **Power-On Sequence** — **chosen.** Evolves the existing Calibration Bench tokens/fonts rather than replacing them; treats the landing page as an instrument "powering on" once (not looping/decorative motion): the logo draws itself in, the headline resolves as a monospace readout, three progress bars sweep to their resting values, and the standards row ticks in sequentially.
3. **The Co-Pilot Bench** — evolves Calibration Bench with one new "ember" accent and a live-thinking ticker. Rejected: the "ember" accent is a new token the user didn't ask for, and the typing-ticker motif read as closer to generic AI-chat styling than the instrument-panel metaphor already established.

Power-On Sequence was chosen because it fixes the actual defect (an unstyled screen inconsistent with the rest of the app) without introducing new tokens, fonts, or a second design language — the lowest-risk option that best fits a redesign explicitly meant to unify, not fragment, the app's visual identity.

## Scope

**This spec covers Phase 1 only: the landing/intro screen.** Three phases were agreed for the full redesign:

1. **Phase 1 (this spec)** — visual language + landing screen.
2. **Phase 2 (future spec)** — apply the same language to the interactive flow: the 11-question dialogue, review screen, sidebar.
3. **Phase 3 (future spec)** — re-evaluate/migrate the existing Calibration Bench components (`ledger_components.py`, `theme.py`'s consumers) under the confirmed language, if Phase 1/2 change it further.

A separate, unrelated work stream — a Playwright Page Object Model test suite — was requested by the user but is explicitly **not** part of any of these three phases; it gets its own spec later.

## Design

### Where the code lives

A new module, `src/landing_hero.py`, follows the existing `ledger_components.py`/`theme.py` pattern: pure functions that generate HTML/CSS strings, no Streamlit dependency where avoidable (so they're unit-testable without a Streamlit runtime, matching `theme.py`'s `build_css()`). Imported lazily inside `render_intro()`, matching how `ledger_components.py` is already imported lazily at each call site in `app.py`.

`theme.py` is **not modified** — no new color tokens, no new fonts, no new global CSS rules. Power-On Sequence explicitly reuses the existing `LIGHT_TOKENS`/`DARK_TOKENS` palette values and the already-embedded Plex Sans/Mono/Cond fonts from `_theme_fonts.py`. All new CSS this phase needs (the draw-in/reveal/fill/tick-in keyframes, the new landing-card hover rule) is self-contained: embedded as a `<style>` block inside the HTML string `landing_hero.py` returns, scoped to landing-only class names, not appended to `theme.py`'s `build_css()`. This keeps the new rules out of the global stylesheet the dialogue/review/output screens also load, so nothing here can leak into Phase 2/3 screens ahead of schedule. `landing_hero.py`'s functions still read color values from the `tokens` dict passed in by the caller (same pattern as `build_css(tokens)`) — they just don't live inside `theme.py`'s own stylesheet string.

### What changes in `render_intro()`

The native `st.info()`/`st.success()`/`st.columns()` blocks are replaced with custom markup rendered via `st.markdown(..., unsafe_allow_html=True)`:

- Logo mark redrawn as inline SVG with a `stroke-dashoffset` draw-in animation (~1.1s, once on load).
- Headline revealed via a clip-path "readout" animation (~0.9s), not a generic fade.
- Three progress bars (Risk / Effort / Strategy) sweeping from 0 to a resting value, using the existing `pass_`/`hold`/`accent` tokens — a genuine preview of the Signal Ledger component the user sees later in the real flow, not decorative.
- Standards row (ISTQB / OWASP / IEEE 829 / ISO 25010) ticking in as a staggered checklist.
- The existing three "How it works" cards get a staggered fade-in and a hover state (border + lift). **Correction from an earlier draft of this spec:** `.ledger-card` (used by the dialogue screen's question cards) has no `:hover` rule defined in `theme.py` today — there is no existing hover language to reuse. This is a new hover treatment, scoped to a new landing-only CSS class (not `.ledger-card`, and not added to `theme.py`) so it can't leak onto the Phase-2 dialogue screen ahead of schedule.
- The two real navigation buttons (`st.button` for Start / Review an existing document) stay native Streamlit — only their surrounding visual context changes, not the interaction/routing logic.
- All animations are one-shot on page load (no infinite loops except where the existing `prefers-reduced-motion` global rule in `theme.py` already zeroes out durations for users who've disabled motion — no additional accessibility work needed there).

### Testing

- A unit test for `landing_hero.py`'s pure HTML-generating function(s), following `tests/test_theme.py`'s pattern (call the function directly, assert on the returned string — no Streamlit runtime needed).
- A Playwright script (per today's new `ci-check`-adjacent workflow) to screenshot the redesigned landing page before/after and confirm the animations actually run and that `prefers-reduced-motion: reduce` genuinely disables them — this becomes the first real case for the separate POM test-suite work stream.

## Non-goals

- No changes to the dialogue, review, or output (Risk Register/Effort/Strategy/Test Plan/Document Review) screens — Phase 2/3.
- No new color tokens or fonts.
- No PDF export changes — `pdf_export.py`/`ai_disclosure.py` are untouched; this is a live-app-only visual change.
- No Playwright POM test suite in this spec — separate work stream, own future spec.
