# V3.1 Implementation Plan: Evaluation Package

**Scope:** v3.1 becomes the "evaluation" release. It ships three capabilities as one coherent package:

1. `assess_qa_maturity` (already planned, MCP_PLAN.md section 10) - process-level audit
2. **F1: QA Document Quality Review** - document-level review with a deterministic ISTQB/IEEE-grounded rubric (inspired by Testomat.io's Test Case Quality Review, lifted to document level)
3. **F2: Test Results Analysis** - deterministic health metrics from real test execution results (JUnit XML / CSV), feeding the Risk Register (inspired by Testomat.io's Analytics: flaky / never-run / ever-failing / slowest / failure clustering)

Together they turn QAI Consultant from a forward-only generator into a tool that also **evaluates what already exists**: process (maturity audit), documents (quality review), and execution data (results analysis).

This plan covers F1 and F2. `assess_qa_maturity` keeps its existing spec in MCP_PLAN.md and should be built in the same release; where the three share infrastructure (rubric pattern, citation format), F1/F2 must follow whatever `assess_qa_maturity` lands first, or vice versa - do not create two rubric formats.

---

## 1. Locked decisions

- **The MCP lens governs everything** (MCP_PLAN.md section 1): the MCP server never generates text. Both new MCP tools are deterministic + retrieval only. LLM narrative on top of the deterministic outputs happens exclusively in Streamlit/CLI via the existing `LLMClient`.
- **New core modules are keyless and dependency-free** in their import graph (pattern: `src/effort_core.py`, `src/kb_config.py`). No imports of `agent.py`, `streamlit`, `pinecone`, `mistralai` from `review_core.py` or `results_core.py`. This is what makes them shippable in the PyPI wheel and testable on a bare CI box.
- **Determinism is the contract:** same input, same score / same metrics, always. The eval functions are the assertions (same philosophy as `evals/`).
- **Citations come from the local index**, not hardcoded: rubric dimensions map to retrieval queries against `knowledge_base/` (`LocalIndex.search()` on the MCP path, Pinecone `retrieve_knowledge()` on the Streamlit path). A gap without a citable source is reported without citation rather than with a fabricated one.
- **Versioning:** `version.py` bumps to `3.1.0`; `pyproject.toml` version follows. New modules ship in the wheel (update the packaging whitelist in `tests/test_packaging.py` accordingly - it exact-matches the module set).
- **Branch:** implement on a new branch `feat/v3.1-evaluation-package` off `master` (note: v3.0 merge to master may still be pending - check `git branch` and confirm base with the user before starting).

## 2. F1: QA Document Quality Review

### 2.1 What it does

User provides an existing QA document (Test Plan, Test Strategy, or a test case list in markdown/plain text). The system returns:

- **Overall score 0-100** plus per-dimension scores
- **Findings list**: each finding = {dimension, severity (critical/major/minor), what is missing or weak, evidence (the matched/missing pattern), kb_citations []}
- On the Streamlit path only: an LLM-written narrative review grounded in the findings + RAG chunks

### 2.2 Rubric dimensions (deterministic)

Six dimensions, each scored 0-100 from mechanical checks, overall = weighted mean (weights sum to 100, normalize at runtime like `ACTIVITY_BREAKDOWN` does - see the PERT normalization gotcha in CLAUDE.md):

| Dimension | Weight | Deterministic checks (examples, not exhaustive) |
|---|---|---|
| Structure completeness | 25 | Required sections present per doc_type (IEEE 829 for test plans: scope, items, features to be tested / not to be tested, approach, pass/fail criteria, suspension/resumption, deliverables, schedule, risks, approvals). Regex/heading matching, case-insensitive, synonym lists per section. |
| Objectives & scope clarity | 15 | Scope section exists and contains both in-scope and out-of-scope signals; objectives are present and non-empty; doc states the test levels/types addressed. |
| Entry / exit criteria | 15 | Explicit entry and exit criteria sections or inline criteria; exit criteria contain at least one measurable expression (number, %, "all ... pass", coverage threshold). |
| Traceability | 15 | References to requirements/user stories/risk IDs (pattern classes: REQ-, US-, JIRA-style keys, "risk R" refs, traceability matrix mention). For test case lists: each case references a requirement or feature. |
| Measurability of expected results | 15 | Anti-pattern detection: vague expected results ("works correctly", "as expected", "should work") counted against total expected-result statements; presence of concrete metrics/KPIs (defect density, coverage %, pass rate). |
| Risk coverage | 15 | Risk section present; risks have severity/likelihood or priority markers; mitigation mentioned; risk-based prioritization signal in approach. |

`doc_type` in {"test_plan", "test_strategy", "test_cases"} selects which section checklist applies (test strategy checklist derives from ISTQB CTAL-TM strategy content, not IEEE 829). `doc_type="auto"` runs a cheap classifier (heading keyword votes) and reports which type it assumed.

Scoring per dimension is a pure function of counted evidence (e.g. sections_found / sections_required scaled to 0-100, vague-result ratio inverted). All thresholds live in module-level constants with one comment line of rationale each (pattern: `evals/thresholds.py`).

### 2.3 New module: `src/review_core.py`

```python
@dataclass
class ReviewFinding:
    dimension: str
    severity: str            # "critical" | "major" | "minor"
    message: str             # human-readable, factual, no LLM
    evidence: str            # matched text or the name of the missing section
    citation_queries: list[str]  # retrieval queries the caller resolves to citations

@dataclass
class ReviewResult:
    doc_type: str            # resolved type (after auto-detection)
    overall_score: int       # 0-100
    dimension_scores: dict[str, int]
    findings: list[ReviewFinding]
    stats: dict              # word count, section count, headings found, etc.

def review_document(text: str, doc_type: str = "auto") -> ReviewResult: ...
```

Key implementation notes:

- Findings carry `citation_queries` (strings) instead of resolved citations, keeping `review_core.py` free of any index dependency. The MCP layer and the Streamlit layer resolve them through their respective retrieval paths and attach `kb_citations` themselves.
- Input hygiene: strip YAML front matter (the app's own outputs carry the Article 50(2) front matter from `ai_disclosure.build_front_matter()`), strip the AI footer, normalize line endings, cap input length (500k chars, structured error beyond).
- Empty/too-short input (< 200 chars after stripping) returns a structured "insufficient_content" result, not an exception.

### 2.4 MCP tool (in `src/mcp_server.py`)

```python
@mcp.tool()
def review_qa_document(document_text: str, doc_type: str = "auto") -> dict:
```

- Calls `review_core.review_document()`, then resolves each finding's `citation_queries` via `_get_index().search(q, k=2)` and attaches `kb_citations: [{"source", "category", "score"}]`.
- Returns `asdict()`-style plain dict: {doc_type, overall_score, dimension_scores, findings, kb_version}.
- Error contract identical to existing tools (MCP_PLAN.md section 3): invalid `doc_type` returns `{"error": "invalid_argument", ...}`, never raises.
- Telemetry: one opt-in event `review_qa_document` with {doc_type, overall_score bucket, finding_count} - no document text, ever (telemetry rule: no free-text payloads).
- Docstring must state clearly that the score is deterministic and the client LLM should write its own narrative from the findings.
- **Warmup gotcha:** this tool touches the embedding model via citations. The existing `index.search("warmup", k=1)` before `mcp.run()` already covers it - do not remove or reorder it (see the Windows stdio deadlock gotcha in CLAUDE.md).

### 2.5 Streamlit UI

New top-level mode on the intro screen: alongside "Generate documents" flow, add **"Review an existing document"**:

- `st.file_uploader` (.md, .txt) + paste textarea; doc_type selectbox (auto/test plan/strategy/test cases).
- Step 1 (instant, deterministic): score card (overall + per-dimension bar/metric row) + findings table. No LLM call yet.
- Step 2 (button "Generate narrative review"): builds a prompt from findings + RAG chunks (`retrieve_knowledge` on citation queries, k=5 total) and streams via `st.write_stream(agent.ask_streaming(...))`. Same per-step try/except pattern as `render_strategy()`, including the `except (StopException, RerunException): raise` guard BEFORE `except Exception` (mandatory - see CLAUDE.md gotcha).
- Save/download: review report saved to `output/quality_review_ProjectName_TIMESTAMP.md` through the same `save()` conventions - filename sanitization regex, `with_ai_footer()`, `build_front_matter()`, and PDF via `markdown_to_pdf()` with `pdf_meta_html()`. PDF bytes cached in `st.session_state.review_pdf_bytes` (never computed in the tab render block).
- **Session state:** all new keys (`review_input_text`, `review_result`, `review_narrative`, `review_pdf_bytes`, uploader keys) must be added to BOTH cleanup lists ("Start Over" and "Generate Another Strategy") - see the session state cleanup gotcha.
- This mode does not consume `run_count` for the deterministic step; the narrative LLM step does (decide: reuse run_count or leave narrative un-metered - default: count it, it is an LLM call).

### 2.6 CLI

`python src/cli.py --review path/to/doc.md [--doc-type test_plan]`: prints score card + findings via `rich` table, offers the narrative step, saves via the same save path. Keep it thin - all logic in `review_core` + shared prompt builder.

## 3. F2: Test Results Analysis

### 3.1 What it does

User provides test execution results (one or more JUnit XML files, or a CSV). The system computes deterministic health metrics and (Streamlit path) injects a summary into the Risk Register generation so risks are grounded in real execution data, not only the 11-question interview.

### 3.2 New module: `src/results_core.py`

Dependency-free (stdlib only: `xml.etree.ElementTree`, `csv`, `io`, `re`, `dataclasses`, `statistics`).

```python
@dataclass
class TestRecord:      # one test in one run
    run_id: str; name: str; classname: str; status: str  # passed|failed|error|skipped
    duration_s: float; message: str  # failure/error message, "" otherwise

@dataclass
class ResultsAnalysis:
    runs: int
    total_tests: int             # distinct test identities
    executions: int
    overall_pass_rate: float
    flaky: list[dict]            # {test, pass_rate, runs} within flaky band
    ever_failing: list[dict]     # never passed, >= min_runs executions
    never_run: list[dict]        # only when a reference test list is provided
    slowest: list[dict]          # top N by mean duration, {test, mean_s, max_s}
    failure_clusters: list[dict] # {signature, count, sample_tests[], sample_message}
    per_run: list[dict]          # {run_id, passed, failed, skipped, duration_s}
    warnings: list[str]          # parsing issues, ignored files, etc.

def parse_junit_xml(content: str, run_id: str) -> list[TestRecord]: ...
def parse_results_csv(content: str) -> list[TestRecord]: ...   # documented column contract
def analyze(records: list[TestRecord],
            reference_tests: Optional[list[str]] = None,
            flaky_min: float = 0.2, flaky_max: float = 0.8,
            min_runs_for_verdict: int = 3,
            slowest_n: int = 10) -> ResultsAnalysis: ...
def summarize_for_prompt(analysis: ResultsAnalysis, max_chars: int = 1500) -> str: ...
```

Implementation notes:

- **Test identity** = `classname + "::" + name` (normalized whitespace). Parametrized test names: strip trailing `[...]` param blocks for identity grouping but keep the raw name in samples.
- **Flakiness** (Testomat.io semantics): pass_rate strictly inside (flaky_min, flaky_max) AND executions >= min_runs_for_verdict. A test with 1 fail out of 2 runs is "insufficient data", not flaky.
- **Ever-failing** requires >= min_runs_for_verdict executions and zero passes.
- **Failure clustering is deterministic string normalization, not LLM:** signature = failure message with numbers, hex ids, quoted strings, file paths and durations replaced by placeholders, truncated to 200 chars; cluster by exact signature match. Good enough to group "TimeoutError waiting for #btn-42" style families.
- **Robust parsing:** accept both `<testsuites>` and single `<testsuite>` roots; missing time attributes default to 0.0 with a warning; malformed XML returns a structured error, never raises to the caller.
- **No file I/O in this module** - callers read files and pass strings (keeps it trivially testable and MCP-safe).

### 3.3 MCP tool (in `src/mcp_server.py`)

```python
@mcp.tool()
def analyze_test_results(junit_xml: Optional[str] = None,
                         csv_text: Optional[str] = None,
                         reference_tests: Optional[list[str]] = None,
                         flaky_min: float = 0.2, flaky_max: float = 0.8) -> dict:
```

- Exactly one of `junit_xml` / `csv_text` must be provided; `junit_xml` may contain multiple concatenated reports? **No** - keep it simple: one call = one run for XML. For multi-run flakiness over MCP, accept a JSON list variant: if `junit_xml` starts with `[`, treat it as a JSON array of {"run_id", "xml"} objects. Document this in the docstring.
- Fully keyless and index-free (no embedding model involved): pure `results_core`.
- Error contract as everywhere: `{"error": "invalid_argument", ...}` for bad/missing input.
- Telemetry event `analyze_test_results` with counts only.
- Clamp: total input size 10 MB, executions cap 500k, structured error beyond.

### 3.4 Streamlit integration (the actual value: data-grounded Risk Register)

- In `render_review()` (the pre-generation review step), add an optional expander **"Attach test execution results"**: multi-file `st.file_uploader` (accept .xml, .csv). Each XML file = one run (run_id = filename).
- On upload: parse + `analyze()`, show a compact metrics panel (runs, pass rate, flaky count, ever-failing count, top clusters). Store `st.session_state.results_analysis`.
- **Risk Register grounding:** `RiskAnalyzer.analyze()` gains an optional `results_summary: Optional[str] = None` parameter; when present, `build_risk_prompt()` appends a clearly delimited block: "MEASURED EXECUTION DATA (deterministic, from user-provided results): ..." using `summarize_for_prompt()`. The prompt must instruct the model to treat these as evidence for specific risks (e.g. flaky suite -> unreliable regression signal risk) and to cite them as [Execution Data] rather than [Source N].
- `generate_all()` passes it through. Absence of results changes nothing (parameter defaults preserve all current call sites and tests).
- The Effort Estimator's data quality score may optionally award points when execution data is attached - only if it can be done without disturbing `test_confidence_v06.py` expectations; otherwise leave effort untouched in this release and note it as follow-up.
- **Session state cleanup:** add `results_analysis` + uploader keys to both cleanup lists.
- The metrics summary is included in the saved Risk Register document (as an appendix section) so the document is self-contained.

### 3.5 CLI

`python src/cli.py --results path1.xml path2.xml` flag on the normal flow: parse, show `rich` metrics table, pass summary into the risk step. Optional in this release if time-boxed; MCP + Streamlit are the priority.

## 4. Evals (release gate additions)

Extend the existing two-tier gate (`evals/run.py`); both additions are tier-1-style: deterministic, keyless, CI-safe.

1. **`evals/review_integrity.py`** + `review_golden.jsonl`:
   - Golden docs: (a) a strong IEEE-829-shaped test plan (score floor, e.g. >= 75), (b) a deliberately weak doc (score ceiling, e.g. <= 40), (c) a vague-expected-results fixture where the measurability dimension must be the lowest-scoring one, (d) an empty/short input producing `insufficient_content`, (e) determinism: same doc scored twice, identical result.
   - Metric names: `score_ordering` (strong > weak by >= 20 points), `dimension_attribution`, `determinism`, `insufficient_content_handling`.
2. **`evals/results_integrity.py`** + fixtures (small JUnit XML files under `evals/fixtures/`):
   - Cases: flaky detection with hand-computed pass rates; ever-failing vs insufficient-data distinction; cluster count on a fixture with 3 message families; malformed XML producing a structured error; CSV/XML parity on the same logical data.
3. Wire both into `evals/run.py` and `thresholds.py` (every floor gets its one-line rationale, per the existing convention).

## 5. Build order (the script for the coding agent)

Each step lands with its own tests and a green run of the FULL existing suite (`python -m pytest tests/ -v`) plus `ruff check src/ tests/` before moving on. Do not start a step until the previous one is green.

1. **`src/results_core.py` + `tests/test_results_core.py`** (~25 tests: parsers, identity normalization, flaky/ever-failing/never-run boundaries, clustering, summarize_for_prompt length cap, malformed input). Pure module, no other file touched.
2. **`src/review_core.py` + `tests/test_review_core.py`** (~30 tests: per-dimension scoring on minimal fixtures, doc_type auto-detection, front-matter/footer stripping, weight normalization guard, determinism, insufficient content). Pure module.
3. **MCP tools:** `analyze_test_results` + `review_qa_document` in `src/mcp_server.py`; extend `tests/test_mcp_server.py` (tool registration, happy path, error contract, telemetry silence when disabled, citation attachment for review). Update `INSTRUCTIONS` string to mention the two new tools. Verify the warmup ordering is untouched.
4. **Packaging:** add both modules to `pyproject.toml` module list; update `tests/test_packaging.py` whitelist; build the wheel and let the licensing/packaging tests prove it.
5. **Streamlit F1 (review mode):** intro-screen entry point, deterministic score view, narrative step, save/PDF path with Article 50(2) marking, session-state cleanup additions. Tests in a new `tests/test_app_review_mode.py` (pattern: existing `test_app_*` tests - mock streamlit session, assert state transitions, cleanup lists, StopException guard presence).
6. **Streamlit F2 (results upload + risk grounding):** `render_review()` expander, `RiskAnalyzer.analyze(results_summary=None)` param, prompt block, `generate_all()` passthrough, Risk Register appendix, cleanup additions. Extend `tests/test_risk_analyzer.py` + new `tests/test_app_results_upload.py`. All existing risk/analyzer/integration tests must pass UNCHANGED (the parameter is optional).
7. **CLI flags** (`--review`, `--results`) - thin wrappers; extend CLI tests minimally.
8. **Evals:** step 4 section above; `python -m evals.run --det` green.
9. **Docs and version:** `version.py` -> 3.1.0, `CHANGELOG.md` entry, CLAUDE.md (architecture table rows for the two new modules, new gotchas if any found, roadmap v3.1 line updated to the package scope), `README_MCP.md` tool list, MCP_PLAN.md section 10 v3.1 updated to reference this file. In-app Release Notes panel picks up CHANGELOG automatically.
10. **Manual end-to-end pass** on Windows: Streamlit both new flows, `python src/mcp_server.py` via a real MCP client call of both new tools (subprocess stdio, not in-process - the deadlock class of bugs only shows there).

Steps 1-2 are pure additions (zero regression risk). The only step touching existing generation behavior is 6, and it is behind an optional parameter.

## 6. Acceptance criteria

- Both MCP tools callable keyless on a clean machine; deterministic (identical outputs across repeated calls); error contract structured, never raising.
- `review_qa_document`: strong fixture scores >= 20 points above weak fixture; every finding with resolvable sources carries at least one KB citation; no LLM anywhere in the call path.
- `analyze_test_results`: hand-computed golden metrics match exactly; malformed input never crashes the server.
- Streamlit: review mode produces a saved, Article-50-marked report (md + PDF); results upload changes the Risk Register content (visible [Execution Data] grounding) and nothing else in the pipeline; both "Start Over" paths fully clean the new state.
- Full test suite green, ruff green, `python -m evals.run --det` green including the two new integrity modules.
- No new runtime dependency added (stdlib parsing only; embedding model reuse only through existing `LocalIndex`).

## 7. Out of scope (explicitly)

- No test management features (runs, execution tracking, CI listeners, dashboards) - QAI stays a consultant, not a TMS.
- No LLM calls in the MCP server, no exceptions.
- No persistence of uploaded results or reviewed documents beyond the session and the user's own `output/` files.
- Requirements-to-test-case generation (Testomat.io idea #4) and free-form "chat with docs" (idea #5): deferred, candidate for v3.2+ discussion.
- Effort model changes driven by execution data: follow-up, only noted in step 6 of the build order.
